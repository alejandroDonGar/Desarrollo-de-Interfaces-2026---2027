📘 Provider explicado muy fácil

Requisitos de finalización
📘 UT2 · Provider explicado muy fácil

La idea en cuatro frases

  1. Envolvemos la aplicación con un widget que se llama proveedor (ChangeNotifierProvider). Él pone un objeto al alcance de todos los widgets que tiene debajo.
  2. Ese objeto es un notificador de cambios (ChangeNotifier): una clase nuestra que guarda los datos, los cambia y avisa cuando han cambiado.
  3. Si un widget quiere provocar un cambio, usa read para obtener el objeto y llamar a uno de sus métodos: context.read<Varita>().lanzarHechizo().
  4. Si un widget quiere mostrar un dato y enterarse de cuándo cambia, usa watch para obtener el objeto y consultar sus datos (normalmente, sus variables): context.watch<Varita>().encendida.
🦉 Piénsalo como el correo de lechuzas de Hogwarts. El notificador es la oficina de lechuzas: guarda las noticias y, cuando hay una nueva, envía una lechuza a todos los suscritos. Quien hace watch está suscrito: le llega la lechuza y actualiza lo que muestra. Quien hace read se acerca a la oficina a dejar una noticia, pero no se suscribe.

¿Por qué lo necesitamos?

Hasta ahora, cuando un hijo quería cambiar un dato del padre, el padre le pasaba una función (callback). Funciona muy bien entre padre e hijo. Pero si el botón está muy abajo en el árbol y el dato se muestra en otra rama (por ejemplo, en la AppBar), la función tiene que ir pasando por varios widgets que solo la transportan. Provider evita ese viaje: cualquier widget que esté debajo del proveedor puede encontrar el objeto directamente.

Las piezas

Pieza Qué es En una frase
ChangeNotifier Clase de Flutter de la que heredamos (extends) «Guardo los datos y sé avisar».
notifyListeners() Método que heredamos de ChangeNotifier «¡Atención, mis datos han cambiado!». Se llama después de cambiar el dato.
ChangeNotifierProvider Un widget que envuelve a otros «Creo el objeto y se lo ofrezco a todos los de debajo».
context.read<T>() Busca el objeto de tipo T «Dame el objeto, que quiero pedirle que haga algo». Se usa en los eventos, como onPressed.
context.watch<T>() Busca el objeto y se suscribe a él «Dame el objeto y vuelve a dibujarme cuando avise». Se usa dentro de build.

T es el nombre de nuestra clase, el tipo de objeto que buscamos; en el ejemplo, Varita. context es la posición del widget en el árbol: desde ahí se busca hacia arriba hasta encontrar el proveedor.

El recorrido de una pulsación

👆 Pulso el botón→ read busca el objeto→ el método cambia el dato→ notifyListeners() avisa→ los widgets con watch se redibujan

Ejemplo completo: ¡Lumos!

Una varita que se enciende y se apaga. El botón provoca el cambio (read) y la luz lo escucha (watch). Fíjate en que ningún widget es StatefulWidget y no hay ningún setState: el dato vive en el notificador.

import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

// 1. El notificador de cambios: guarda el dato y avisa cuando cambia.
class Varita extends ChangeNotifier {
  bool encendida = false;

  void lanzarHechizo() {
    encendida = !encendida; // primero cambiamos el dato...
    notifyListeners(); // ...y después avisamos
  }
}

// 2. El proveedor envuelve la aplicación.
void main() {
  runApp(
    ChangeNotifierProvider(
      create: (context) => Varita(),
      child: const MiApp(),
    ),
  );
}

class MiApp extends StatelessWidget {
  const MiApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      home: Scaffold(
        appBar: AppBar(title: const Text('Pasillo del castillo')),
        body: const Center(
          child: Column(
            mainAxisSize: MainAxisSize.min,
            children: [
              LuzVarita(),
              SizedBox(height: 24),
              BotonHechizo(),
            ],
          ),
        ),
      ),
    );
  }
}

// 3. watch: este widget ESCUCHA. Se vuelve a dibujar cuando la varita avisa.
class LuzVarita extends StatelessWidget {
  const LuzVarita({super.key});

  @override
  Widget build(BuildContext context) {
    final varita = context.watch<Varita>();
    return Icon(
      Icons.auto_awesome,
      size: 120,
      color: varita.encendida ? Colors.amber : Colors.grey,
    );
  }
}

// 4. read: este widget PROVOCA el cambio. No necesita escuchar.
class BotonHechizo extends StatelessWidget {
  const BotonHechizo({super.key});

  @override
  Widget build(BuildContext context) {
    return ElevatedButton(
      onPressed: () {
        context.read<Varita>().lanzarHechizo();
      },
      child: const Text('¡Lumos! / ¡Nox!'),
    );
  }
}
  • encendida = !encendida: el operador ! da la vuelta al booleano (true pasa a false y al revés).
  • create recibe una función que crea el objeto. Solo se crea uno, y todos los widgets comparten ese mismo.
  • LuzVarita y BotonHechizo están en ramas distintas y ninguno recibe nada por su constructor: los dos encuentran la varita a través del proveedor.

👀 ¿Qué hace exactamente la línea del watch?

final varita = context.watch<Varita>();

Hace dos cosas: nos da la varita y apunta este widget en la lista de los que quieren enterarse de sus cambios. Es como decir: «apúntame a la lista».

En ese momento no se redibuja nada. El redibujado llega después: cuando alguien pulsa el botón y la varita ejecuta notifyListeners(), Flutter vuelve a ejecutar el build de todos los widgets apuntados, y cada uno lee el valor nuevo. Como la línea está dentro de build, cada vez que se redibuja vuelve a apuntarse, así que sigue escuchando.

Con read obtenemos la misma varita, pero sin apuntarnos. Si LuzVarita usara read, el dato cambiaría por dentro y la luz no se encendería en pantalla.

🤔 ¿Y por qué ya no hace falta un StatefulWidget?

Hasta ahora el dato vivía dentro del widget, y la única forma de pedir «redibújame» era setState(), que solo existe en la clase State. Ahora el dato vive fuera, en el notificador, y es él quien avisa.

Cómo se redibuja un widget Quién lo provoca ¿Tiene que ser Stateful?
Su padre se redibuja y lo vuelve a construir El padre No
setState() El propio widget, que guarda el dato Sí
context.watch<T>() + notifyListeners() El notificador compartido No

En una frase: setState dice «redibújame a mí»; watch dice «redibújame cuando cambie este objeto».

Para recordar

🔔 ¿Cambias el dato? Cámbialo y llama a notifyListeners().

✋ ¿Quieres provocar un cambio? En el evento: context.read<T>().metodo().

👀 ¿Quieres mostrar el dato? En build: final x = context.watch<T>();

Prepara tu proyecto

Provider es un paquete externo. Añádelo desde la terminal, dentro de la carpeta del proyecto:

flutter pub add provider

Y en main.dart importa package:provider/provider.dart.

Errores típicos

  • ProviderNotFoundException: el widget no está debajo del proveedor. Comprueba que el proveedor envuelve la app y haz un hot restart (el hot reload no basta).
  • Pulso y no cambia nada en pantalla: te falta notifyListeners(), o el widget que muestra el dato usa read en lugar de watch.
  • Error al usar watch dentro de onPressed: en los eventos se usa read; watch solo en build.
